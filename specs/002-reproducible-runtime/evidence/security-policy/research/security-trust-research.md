## Proposed authority and record lifecycle

Separate three inputs: protected validator/rules at verified policy revision P; candidate disposition proposals treated only as data; live native human review. A candidate file, local Boolean, chat receipt or scanner result cannot supply the third input. For bootstrap, a trusted validator at P may assess a proposed data set after authenticating its human review; it must not import candidate validator/configuration code. After legitimate merge, the protected registry is authoritative data, still subject to native revocation checks. Merely appearing on main is not a substitute for the required review witness.

Define one canonical UTF-8 serialization of a versioned disposition set, reject unknown/duplicate keys and duplicate/ambiguous rows, sort by exact identity, and hash it with a domain-separated SHA256. Its digest D must cover repository ID/name, scanner version and executable-artifact identity, full scanner configuration/default-rule/command-policy digest, scan mode, native fingerprint/rule, repository-relative path, complete source range, and independently resolved Git blob ID plus SHA256 bytes. History rows also bind the exact finding commit. Keep approval metadata outside the self-hashed row set.

Require an authenticated native `APPROVED` review on the exact proposal head, with explicit D and substantive false-positive rationale; independently fetch the proposal/blob at that review's `commit_id` and recompute D. Record review ID, immutable reviewer ID, PR, reviewed head, P, D, native submission/state and source/report identities in the issuer receipt. Derive head/tree identity from native metadata rather than embedding a commit's own hash in its source file. Candidate-authored provenance references are lookup hints, never authority.

Suggested states: **proposed → authenticated for one candidate → active after legitimate protected merge → revoked/superseded**. Ordinary head changes invalidate proposal approval. Active historical records retain their immutable finding commit/blob binding, but live native review, role, protected rules and scanner-policy checks must still pass. An active record's approval PR is closed/merged: upstream `validate_candidate` (140) explicitly requires an open PR, so do not reuse it unchanged. Add a merged-record verifier that checks native merged state, reviewed proposal content/digest, merge/protected-ledger provenance and current approval state. Define/test squash/rebase mapping rather than assuming the reviewed head is an ancestor of main.

Current-tree and history identities are disjoint. A history approval cannot match a tree row. Conservative recommendation: grant tree approval only for its explicitly reviewed scan tree plus exact path/blob/range/rule; no automatic carry to a changed tree. Carrying an unchanged blob across later unrelated tree revisions is a separate human policy choice, not implied by this direction. Any scanner/configuration/rule change invalidates affected records until requalified and reapproved; never silently migrate identities. A missing, dismissed, superseded-by-changes-requested, mismatched or unresolvable approval means no acceptance. Retain prior records as audit history; do not erase the native finding.

## Concrete threats and missing gates

1. **Upstream does not establish human presence.** `eligible` (132) and `matching_role` (101) do not inspect `user.type`. An offline probe against the pinned `require_approval` accepted a synthetic `type: Bot` maintain-role reviewer. This is a constructor-level limitation, not evidence of a real Bot's permissions. Add native `User`/protected-human-ID checks. Even `User` attribution cannot prove manual human action if automation holds that account's credential: keep eligible approver credentials out of agents/workers and document the human-controlled review boundary. GitHub permits App installation tokens to create reviews; platform attribution alone must not be mislabeled human-presence proof. [Review API](https://docs.github.com/en/rest/pulls/reviews).
2. **Native green jobs do not attest scanner output.** `execution_policy.require_matrix` (93) binds IDs/head/attempt/job names and success, but never proves which scanner/configuration produced an artifact. Candidate-edited workflows can retain names. Use a trusted, protected-version scan worker; candidate files/Git objects are data only. No candidate install hooks, scripts, actions, submodules or shared executable caches. Scanner/config/empty ignore file/output directory must come from trusted state outside the candidate tree. The worker never receives the issuer App token.
3. **Reports need a new authenticated envelope.** Bind repository/head/base/tree, retained-ref and reachable-history manifest, protected worker/workflow/code revision, run/attempt/job, executable/config/command policy, both required scan modes, exits, report digests and bounded report schemas. Fetch artifacts by native run/artifact identity, not names or candidate paths; validate transport/archive bounds and reject traversal, symlinks, duplicate members and missing files. Resolve every source blob independently from verified Git objects. Hashing a candidate-supplied report does not establish provenance. Preserve donor PR129/history roots; main ancestry alone is insufficient.
4. **Revocation is not automatic in this pin.** `latest_reviews` handles `DISMISSED`, and `evaluate_core` rereads reviews/roles; however `.github/workflows/trusted-policy.yml:3–5` enrolls only `repository_dispatch`. `trusted_event.parse_event` supports dispatch/comment/run, not review-dismissal events. A dismissal unit test proves reevaluation behavior only. Activation needs a trusted dispatcher/trigger path for relevant review/comment/head/policy/role changes, failure replacement of prior success, and a defined merge-freshness boundary. Failures before a target is resolved/published can leave an earlier green check intact; checks do not expire merely because later evidence is unavailable. Do not claim immediate revocation without a tested merge-time/freshness design.
5. **Native exit handling remains separate.** The bounded local qualification observed Gitleaks8.30.1 findings exit42 and fatal-config exit1; it explicitly does not establish release provenance. Accept only exit0+empty report or exit42+nonempty report, both fresh/complete, before disposition. Every other relationship fails. Upstream's general nonzero-fatal runner must be adapted deliberately, never with arbitrary `|| true`; OSV/Opengrep acceptance stays unchanged.

## Bootstrap and unresolved activation decisions

Prepare an empty registry, pure validator and authenticated read-only adapter with positive/negative fixtures. Local receipts must say **preparation / not an App-issued passing check**. Missing App identity/token/installation or native metadata cannot fall back to operator attestation. No individual finding is accepted now.

Activation still requires separate legitimate approval for App/access/protection configuration: install and verify the dedicated App, protected environment/key handling, least permissions, protected workflow/code revision, CODEOWNERS/protection/bypass rules and required check bound to that App ID; read back the resulting native state. Upstream's workflow at lines19–40 assumes those resources already exist. GitHub documents that required checks can select a specific App source, while other write-capable actors can set statuses. [Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). Privileged `workflow_run` execution must never run candidate code or consume executable caches. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).

Human decisions still needed: eligible independent human identities (and whether one is available under the contributor exclusion); exact current-tree lifetime/carry rule; merged approval provenance under allowed merge methods; revocation-to-merge freshness/dispatcher design; native repository/workflow/App identities and retained-history lower bound. Required negative controls include forged native metadata, Bot/machine-account and contributor approval, dismissed review after prior success, policy/head/config drift, forged/partial artifacts, adjacent unapproved finding, duplicate identity, source-blob mismatch, omitted donor history, and wrong App/repository/attempt. None is satisfied by the existing reports or the direction receipt alone.
