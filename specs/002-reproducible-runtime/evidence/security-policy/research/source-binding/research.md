## Chosen minimal implementation

Use Python stdlib plus one explicitly selected native Git executable. Read raw commit/tree/blob objects with `cat-file`, recompute each object OID with native `git hash-object --no-filters -t <type> --stdin` **without** `-w`, `--path`, or `--literally`, and calculate SHA256 over the complete blob bytes independently. Parse the already verified raw tree bytes directly to select exact UTF-8 path components. Do not implement a shell, fetch transport, Git config-policing framework, or a second path lookup after verification.

1. Receive the exact expected source commit separately from restricted native metadata. History requires native commit equal source commit and exact membership in the retained-history set supplied by the caller. Tree findings require the parser's empty native commit and source commit equal the expected scanned head. The caller's set/head remains metadata until the later protected worker proves snapshot/history provenance.
2. Accept only full lowercase40-hex SHA1 identifiers and require Git's storage object format `sha1`. SHA256 repositories and unknown algorithms are unsupported v1 and fail, rather than being sliced to40 characters.
3. Require `cat-file -t <source-oid>` to return exactly `commit`, then read the entire bounded raw `cat-file commit <oid>` body. Recompute its native object OID. The first line must be exactly `tree <full40-hex>\n`; parse that pointer from the verified bytes. Reject tags, including annotated tags that peel to commits, other object types, missing objects, invalid first headers, or hash mismatches.
4. Read and recompute every traversed tree object. Parse each complete tree's entries, select one exact raw-name match for the next requested component, and require canonical directory mode for intermediate components. No filesystem path resolution or symlink following occurs.
5. Require final mode `100644` or `100755` and actual object type `blob`; reject directories, symlinks120000, gitlinks160000, missing/ambiguous names, mode/type disagreement, malformed/truncated trees and unsupported modes.
6. Read the entire bounded blob, recompute its Git OID and full-byte SHA256, then check line bounds. Return restricted immutable metadata/digests with source text omitted from repr and errors. A returned digest is an identity measurement, never a success/approval property.

The raw-type distinction matters: local `cat-file -t` reported `tag` for an annotated blob tag, while `cat-file blob <same-tag-oid>` returned its target bytes. Similarly, `<tag>^{commit}` successfully peeled an annotated commit tag. Therefore typed `cat-file` output or revision peeling alone cannot establish the requested direct object type. The [cat-file manual](https://git-scm.com/docs/git-cat-file/2.50.0) documents direct type inspection, permitted dereferencing and raw object-body output. Native `hash-object --no-filters --stdin` recomputed all three synthetic commit/tree/blob OIDs; `rev-parse --show-object-format=storage` returned `sha1`. The [hash-object manual](https://github.com/git/git/blob/v2.50.1/Documentation/git-hash-object.adoc) distinguishes raw hashing, optional writing, attribute conversion and permissive literal-object mode.

## Why literal ls-tree alone was rejected

The correct diagnostic command is an argv list equivalent to `git --literal-pathspecs --no-replace-objects --no-lazy-fetch --git-dir=<owned-store> ls-tree -z --full-tree --abbrev=40 <full-commit> -- <exact-path>`. Parse NUL records as `mode SP type SP fullOID TAB exact-name NUL`, compare the returned path bytes exactly, and require one record. `--full-tree` avoids working-directory prefix changes; `-z` avoids filename quoting; `--` protects leading dashes. Do not use name-only output because mode/type are necessary. These semantics are documented in [ls-tree](https://github.com/git/git/blob/v2.50.1/Documentation/git-ls-tree.adoc) and the global pathspec switches in [git](https://git-scm.com/docs/git/2.50.0).

The probe passed exact matches for ordinary, nested, space, bracket, star, pathspec-magic-looking, leading-dash and UTF-8 names. Missing paths returned empty output. Output modes distinguished100644,100755,120000,040000,160000.

However, a synthetic loose nested-tree object was replaced with different well-formed tree bytes **under the original tree OID**. Recursive `ls-tree <commit> -- dir/nested.txt` exited0 and mapped the path to the replacement blob. Recomputing that blob's OID alone would pass. Raw tree hashing detected the mismatch. Corrupted root-tree and commit objects were rejected by this local `ls-tree` with exit128; corrupted nested-tree mapping was not. Raw `cat-file` reads succeeded for all corrupted object classes. This is regression evidence for independently hashing every traversed tree, not a claim that all Git object access validates integrity. The distinction follows [object.c](https://github.com/git/git/blob/v2.50.1/object.c) hash-checking parse paths and [tree.c](https://github.com/git/git/blob/v2.50.1/tree.c) recursive `parse_tree` paths. Directly parsing verified raw bytes also removes the verify-then-reread mapping window.

## Raw tree format and canonical v1 boundary

Each entry is ASCII octal mode, one space, nonempty raw filename, NUL, then exactly20 raw OID bytes for SHA1. There is no newline between entries. The next entry starts immediately after those20 bytes. Stored directory mode is `40000`; the displayed ls-tree form is `040000`. Standard stored modes are `100644`, `100755`, `120000`, `40000`, `160000`. Compare only the requested component's exact UTF-8 bytes; unrelated sibling names need not decode as UTF-8. Reject missing delimiters, truncated hashes, trailing unparsed bytes, empty/slash/dot/dotdot names, duplicate names and noncanonical/unsupported modes. Reject an unsupported selected source rather than normalize it into a regular file.

Git's decoder and hash-width handling are in [tree-walk.c](https://github.com/git/git/blob/v2.50.1/tree-walk.c); its `canon_mode` call explains why a stricter raw-mode check is needed. [mktree.c](https://github.com/git/git/blob/v2.50.1/builtin/mktree.c) writes octal mode/name and raw hash bytes. [fsck.c](https://github.com/git/git/blob/v2.50.1/fsck.c) independently diagnoses malformed trees, zero-padded/bad modes, duplicate names and unsorted entries. It only tolerates legacy100664 outside strict mode.

If requiring canonical order, the key for slash-free names is `name + (b'/' if mode == b'40000' else b'\0')`, strictly increasing. This follows Git's `base_name_compare` in tree.c. Also track duplicate **raw names** separately: file/directory duplicates can be separated by other entries under this ordering. The synthetic native tree decoder consumed every byte and confirmed the five stored modes above.

## Environment, replacements, grafts and clean store

Construct a fresh allowlisted subprocess environment; do not copy the parent and remove only a few variables. Inherited `GIT_OBJECT_DIRECTORY` redirected an otherwise existing object to a different scratch database and made it unreadable. Other ambient Git variables can redirect the repository/common directory, alternates, refs/replacements, config parameters, attributes or trace files. Inherited `GIT_CONFIG_COUNT`/keys, `GIT_CONFIG_PARAMETERS`, executable/helper paths, pager/askpass/SSH variables, tracing and dynamic-loader variables must not cross this boundary. Use an absolute trusted Git executable, fixed trusted PATH and locale, explicit absolute owned Git directory, noninteractive stdin and no pager. Set system/global Git config paths to `/dev/null`; the [Git environment documentation](https://git-scm.com/docs/git/2.50.0) describes these controls.

The scope should be a **fresh worker-owned bare store**, populated and qualified later by the protected worker; source-reader fixtures can use owned synthetic stores now. Create it with an explicit empty template and trusted config. Do not copy candidate config, remotes, hooks, replacement refs, graft/shallow files, alternates or caches as authority. No source helper should claim that arbitrary candidate-owned `.git` state is trusted. Local includes are still parsed when global/system config is disabled: a synthetic malformed local include made raw reads fail. A fresh store avoids custom policing of arbitrary candidate configuration. Full object acquisition, frozen refs, completeness, immutability, Git executable provenance and OS qualification remain SEC006+ worker prerequisites.

Always use `--no-replace-objects`. Synthetic replacements changed commit path mapping and blob contents without the flag; the flag preserved original bytes. Legacy `info/grafts` is a separate mechanism: a two-commit `rev-list --count` became1 **even with this flag**, while raw commit bytes still contained the parent. A trusted `GIT_GRAFT_FILE=/dev/null` override restored2 locally, but this is not a substitute for later history/snapshot completeness. [replace documentation](https://github.com/git/git/blob/v2.50.1/Documentation/git-replace.adoc), [replace-object.c](https://github.com/git/git/blob/v2.50.1/replace-object.c) and [commit.c](https://github.com/git/git/blob/v2.50.1/commit.c) show the separate replacement and graft paths.

Raw `cat-file <type> <oid>` plus `hash-object --no-filters` does not request filters, textconv, checkout, hooks, submodules, archive or diff helpers. A scratch configured-program marker stayed absent for raw reads. Positive controls using explicit `--filters` and `--textconv` with active scratch attributes both invoked the marker program. Never add these transformation options to source identity reads; they can execute configured programs and change returned bytes.

## No lazy fetch and supported-platform dependency

Require the fail-visible **global `--no-lazy-fetch` flag**, including in capability qualification; do not rely on an env-only setting that an older executable may silently ignore. Upstream v2.43.0, v2.44.0 and v2.45.0 promisor-remote.c have no `GIT_NO_LAZY_FETCH` guard; v2.46.0 does and its manual documents the flag. See [2.43 source](https://github.com/git/git/blob/v2.43.0/promisor-remote.c), [2.45 source](https://github.com/git/git/blob/v2.45.0/promisor-remote.c), [2.46 source](https://github.com/git/git/blob/v2.46.0/promisor-remote.c) and [2.46 manual](https://github.com/git/git/blob/v2.46.0/Documentation/git.txt). Upstream2.46 is the demonstrated release baseline; exact vendor capability/artifact qualification remains necessary.

On observed `/usr/bin/git` 2.50.1 (Apple Git-155), AppleSilicon arm64, Python3.11.15: the flag capability check succeeded. A missing-object read in a synthetic promisor store exited128 with no scratch remote-helper invocation. Removing the flag invoked the scratch helper (it only wrote a marker and exited; it did not connect anywhere). `GIT_ALLOW_PROTOCOL=''` also prevented the helper in the control and is a useful second barrier: the [Git manual](https://github.com/git/git/blob/v2.46.0/Documentation/git.txt) says it overrides existing per-protocol policies. `protocol.allow=never` alone is weaker because explicit `protocol.<name>.allow` can override the default, per [protocol configuration](https://github.com/git/git/blob/v2.50.1/Documentation/config/protocol.adoc).

Ubuntu24.04 and Python3.11–3.13 remain supported requirements. No Ubuntu runtime or Python3.12/3.13 runtime was exercised here. A default/older Ubuntu Git must be treated as an **unsatisfied worker provisioning/qualification dependency**, not silently accepted or excluded from support. The observed local Git version is usable for preparation controls; this note does not authenticate its release artifact or establish a supported-worker security provenance claim.

## Bounds, line counts and safe failures

Bound actual stdout during reading with a small POSIX `select`/`os.read` loop and monotonic deadline, not `capture_output=True` followed by truncation. Use fixed command forms, validated OIDs, no shell, `stderr=DEVNULL`, isolated process session, and kill/reap on overflow, timeout, nonzero exit, unexpected encoding/schema or incomplete output. Feed bounded hash input through a private temporary file to avoid stdin/stdout pipe deadlock. An object-size preflight helps reject large native allocations, but must not replace the actual read cap. Define command, commit/tree/blob byte, tree-entry, path-depth, total-byte, total-subprocess and total-resolution time budgets. Budget exhaustion fails; never hash or approve a prefix. The worker must later supply process memory/CPU/disk/network isolation; pipe caps do not bound all native memory allocations.

The POSIX spike returned exactly1024 bytes at the cap;1025 bytes and endless output failed with fixed `source command output limit`. Silent hang and stdout-closed-then-hang failed as `source command timeout` in105/103ms for100ms deadlines. Nonzero exit/stderr became fixed `source command failed`; a1MB stderr flood was discarded while2 stdout bytes returned. All raised category errors had suppressed context. These are AppleSilicon/Python3.11 preparation controls, not OS-matrix qualification or process-tree-hosting acceptance.

Use full-blob byte line bounds with no source-character or column slicing. A byte-LF line-count policy gives empty=0, `a`=1, `a\n`=1, `\n`=1, `a\nb`=2, CRLF two lines=2; lone CR and UTF-8 U+2028 do not create extra LF lines. Preserve native columns exactly as already validated positive metadata. This line-count policy must remain aligned with the separately qualified pinned scanner's semantics; this Git-only research does not establish scanner coordinate semantics. Bounds beyond the complete file fail. Current-tree content equality with the actual scanned filesystem, before/after snapshot agreement and all retained-history membership completeness remain later worker proof, not implications of source metadata construction.
